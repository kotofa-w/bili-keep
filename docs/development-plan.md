## 一、目标与本次修订

Bili Keep 继续围绕一个目标：从真实观看中发现可能值得保留的视频，让用户能够整理并找回视频及其中的关键内容。

保留资料库管理、评分深化、片段笔记、智能辅助四个方向，交付顺序调整为：

**整理闭环 → 单点片段与简短笔记 → 评分实验 → 智能辅助。**

先解决能够直接使用的问题；反馈记录随人工整理尽早加入，评分评估工具随后建设。标签、集合、笔记和AI结果不直接增加观看喜好分。

相较原规划，本次主要修订为：

| 原规划不足                             | 修订结果                                                 |
| -------------------------------------- | -------------------------------------------------------- |
| v2备份未覆盖字幕源、删除标记和评分配置 | 明确真源与缓存，新增模块必须同时支持完整备份             |
| 新对象笼统采用时间戳合并               | 分离平台字段与用户字段，明确对象、关系、笔记的冲突与删除 |
| 算法回退与扩展降级混在一起             | 分开验收；未完成恢复演练前不承诺支持扩展降级             |
| 评分反馈仅记录当时分数                 | 保存决策时证据与参数版本，明确标签及评估分母             |
| 只平滑覆盖权重                         | 同时检验投入目标、多P时长口径及边界变化                  |
| Marker依赖保存时的分P序号回跳          | 保存时确认媒体身份，回跳时按CID解析最新序号              |
| 首批同时引入较多抽象与性能设施         | 按实际功能拆分，先测量，再增加缓存或索引                 |
| AI能力依赖尚未验证                     | 将字幕来源和单提供方原型作为独立前置验证                 |

## 三、技术路线与模块边界

采用现有扩展内渐进扩展的路线。相较先搭完整服务框架，这条路线能尽早交付整理功能；相较引入服务器，它也保持当前本地数据边界。代价是搜索和计算受浏览器资源限制，达到实际瓶颈时再针对性优化。

不预建全部`features/`目录、服务类、注册器或空适配器。实现时按职责拆分现有代码：

| 职责           | 输入与输出                                | 边界                             |
| -------------- | ----------------------------------------- | -------------------------------- |
| 采集及位置读取 | 已绑定媒体 → 会话快照或主动标记位置       | 不承担标签、笔记、AI处理         |
| 持久化与迁移   | 经校验的对象 → 事务结果                   | 集中管理schema、索引、版本和合并 |
| 备份           | 一致性真源快照 ↔ 经校验的合并计划         | 不导出密钥，不默默丢弃未知模块   |
| 评分           | 不可变证据、模型及参数 → 分数、贡献、理由 | 纯计算；人工状态在独立规则中合成 |
| 整理与查询     | 用户命令、筛选条件 → 条目或更新结果       | 不修改原始观看证据               |
| 片段与笔记     | 已确认位置、用户文本 → 标记及笔记         | 与观看计分门槛分开               |
| 智能任务       | 明确选择的源文本 → 经校验的建议或摘要     | 不静默改写个人内容及决定         |

优先复用现有函数、类型和页面。只有实际存在第二个实现，或已知环境差异需要隔离时，才增加替换接口；不要求一次重构全部调用方。

## 四、数据与生命周期契约

### 4.1 按阶段增加仓库

| 数据                             | 规划职责                                   | 引入阶段       |
| -------------------------------- | ------------------------------------------ | -------------- |
| `sessions`                       | 原始累计观看会话，保持现有契约             | 已有           |
| `decisions`                      | 手动保留、排除、auto及旧备注，保持兼容     | 已有           |
| `videos`                         | 平台标题、UP主、封面、元数据来源及获取时间 | 整理闭环       |
| `videoStates`                    | 手动收录标识、整理状态、创建及修订信息     | 整理闭环       |
| `tags`、`videoTags`              | 标签及视频关联                             | 整理闭环       |
| `collections`、`collectionItems` | 集合及含顺序的成员关系                     | 整理闭环       |
| `feedbackEvents`                 | 人工操作、决策时证据及撤销关系             | 整理闭环       |
| `tombstones`                     | 新模块对象及关系的删除信息                 | 整理闭环       |
| `markers`、`notes`               | 时间定位与用户正文                         | 片段笔记       |
| `settings`                       | 所选评分模型、非敏感参数及必要个人设置     | 对应功能启用时 |
| `textSources`、`aiArtifacts`     | 字幕/输入文本及版本、AI结果与来源          | 智能辅助       |

这张表是目标职责，不要求首批创建后续仓库。数据库版本、备份协议版本、产品版本分别管理；以后新增仓库继续递增数据库版本。

### 4.2 视频与个人整理

视频以bvid为关联键；分P以CID为身份，part只是顺序提示。`videos`的平台刷新只更新平台字段；用户状态保存在`videoStates`，不随平台元数据覆盖。

整理状态先支持`inbox / later / reviewed / archived`，与`keep / candidate / observed / exclude`独立。查询取手动收录、会话及决定涉及的bvid并集；只有决定、缺少元数据的旧条目也应可见并提供占位信息。

手动添加允许保存合法BV号或视频链接。元数据不可用时可保存待补全条目；明确显示“尚无观看证据”，不生成假会话，不因手动添加自动判为喜欢。之后发生真实观看时合并到同一bvid。

### 4.3 修订、删除与冲突

新模块的可编辑对象及关联记录具有稳定主键、`createdAt`和`updatedAt`；标签重命名、集合成员排序、关联增删均属于修订。关系键分别为`[bvid, tagId]`和`[collectionId, bvid]`。

本地写入使用同一事务完成读取、校验和更新。编辑界面提交时带上所见修订信息；若该对象已变化，提示刷新或处理冲突，不直接覆盖另一页面的新编辑。

导入规则如下：

| 情况                     | 默认处理                                                     |
| ------------------------ | ------------------------------------------------------------ |
| 相同ID、相同内容         | 不重复写入                                                   |
| 旧会话、旧决定           | 沿用现有时间策略，不覆盖较新本地快照                         |
| 新模块普通结构化字段     | 按所属字段域的修订时间合并；同时间内容冲突默认保留本地并报告 |
| 个人笔记或旧备注正文不同 | 不仅凭时间静默覆盖；预览差异，由用户选择或保留冲突副本       |
| 相同规范化标签名、不同ID | 导入前决定合并映射或重命名，同时改写关联；不制造悬空关系     |
| 无效/悬空关联            | 校验阶段拒绝或要求明确修复，不写入半成品                     |

时间戳不证明跨设备因果顺序；当前方案不承诺自动解决跨设备并发。普通结构化合并规则及同时间保留本地策略属于本地导入规则，不承诺导入顺序无关。

新模块删除保留`entityType + entityKey + deletedAt`删除标记；复合关系键使用稳定编码。删除标签/集合只影响对象与关联，不删除会话、视频及笔记；相关关联也记录删除。标记删除保留关联笔记，并将其转为视频级笔记；该变更与删除在同一事务完成。

导入时同时比较对象、关联及删除信息；旧对象不能覆盖较新删除，同时间默认删除优先。重新添加必须是显式的新修订。删除标记纳入备份，首批不自动清理；未来清理需另定不会导致旧备份复活的边界。不同内容的笔记与删除冲突在导入预览中人工处理。

### 4.4 真源与缓存

必须备份的真源：观看会话、手动决定及旧备注、手动收录与整理状态、标签与集合及关联、片段、笔记、反馈及其证据、删除信息、不可重新获得的字幕/源文本、AI结果及来源记录、所选评分版本和非敏感参数。

可重建的数据：列表摘要、评分派生缓存、全文索引和向量索引。丢失缓存不得导致上述真源丢失。只有在重建所需源文本、模型标识和切分规则齐全时，向量才可被视作可重建缓存。

普通备份不含Cookie、SESSDATA、模型密钥或其他凭据。服务连接及凭据单独配置；恢复后提示哪些能力需要重新连接。

## 五、数据库迁移、备份与恢复

### 5.1 迁移流程

1. 核对当前代码、schema及最新资料库备份；开发大改前另核对远端备份状态。
2. 明确本批需要的仓库和索引，再编写顺序迁移及旧版本fixture。
3. 升级事务只做本地结构及必要数据修改，不等待网络、模型或其他异步外部任务。
4. 保留现有`onversionchange`关闭连接，增加`onblocked`提示和失败信息；不自动删除数据库。
5. 可重建的大量派生内容在升级后按可恢复单元生成；完成前可使用兼容查询或明确显示初始化状态。
6. 在隔离环境演练旧库升级、事务失败回滚和备份恢复后，才将新版写入能力交付到日常扩展。

旧`sessions`、`decisions`不得因迁移丢失或改变观看含义。是否从会话回填`videos`由规模测试决定；也可先读取时兼容旧数据，随后幂等补全。

### 5.2 备份v2

使用独立版本的备份封装，建议结构如下。具体字段在整理闭环阶段固定并纳入兼容测试：

```json
{
  "format": "bili-keep",
  "version": 2,
  "exportedAt": "ISO-8601 timestamp",
  "modules": [{ "id": "library-core", "schemaVersion": 1 }],
  "data": {
    "sessions": [],
    "decisions": [],
    "videos": [],
    "videoStates": [],
    "tags": [],
    "videoTags": [],
    "collections": [],
    "collectionItems": [],
    "feedbackEvents": [],
    "tombstones": []
  }
}
```

后续笔记、评分设置、字幕和AI模块增加各自数据及模块schemaVersion。导入器必须理解整份备份声明的模块和版本后才能执行完整恢复；遇到不支持的模块或更高版本，整份拒绝并说明所需版本，禁止静默忽略。首批不提供复杂的部分恢复模式。

导入先检查文件大小，再解析与全量校验对象、关联和容量限制，形成冲突预览；用户完成必要选择后，写入前再次检查受影响本地修订，变化则重新预览。应用合并计划使用覆盖所有相关真源仓库的单一事务，失败整体回滚。不得把用户确认等待或网络操作放在事务内。

导出在同一只读事务中取得一致性真源快照；JSON序列化在读取完成后执行。重复导入不增加相同对象、反馈或冲突副本；冲突副本应保留来源身份以去重。

既有10万记录及5000万字符限制不能直接套用所有新模块：分别定义对象数量、单条文本和总备份大小上限，并在界面提前提示。首批超限清楚拒绝，不引入分批提交后却声称“整份无半写”的恢复模式。

### 5.3 旧格式与回退边界

- 新版可读取v1，保留会话、决定和旧备注，并初始化必要默认值。
- 提供v1兼容导出，仅包含旧格式能够表达的数据；导出前列明省略的标签、笔记等新增内容，并提醒保留完整v2备份。
- 评分回退：在新版内切回v1算法，不降低数据库版本，不改变人工决定。
- 扩展降级：旧2.1.2不能打开更高版本的同名数据库。兼容JSON不能解决这一问题；在专用重建/恢复工具及隔离演练完成前，产品明确不支持直接覆盖旧构建降级。优先前向修复。任何真实库重建均另行获得涉及数据替换的明确授权。
- 上游历史库及其备份始终独立，不纳入本资料库的迁移或重建。

## 六、交付A：资料库整理闭环

### 6.1 用户能够完成的流程

自动候选或手动收录 → 保留/排除 → 标签分类 → 加入集合 → 按条件搜索 → 再次打开。

首批交付包括标签创建/重命名/删除、一视频多标签；集合创建/说明/添加移除/排序；批量设置决定、标签、集合和整理状态；关键词、喜好状态、整理状态、标签、集合、UP主与时间筛选。评分区间沿用当前分数，等评分实验阶段再增加模型对比。

不同筛选维度采用AND；多个标签可选AND/OR；多个集合默认OR。排序先支持最近观看、分数与标题，并用bvid作为相同值的最终排序键。没有观看时间的手动条目在“最近”中使用收录时间，并在界面说明。

“待整理、已保留、待回看、已排除”作为查询视图，不复制视频。“有笔记”在笔记阶段加入。智能集合、保存任意复杂查询和高级标签管理后置。

### 6.2 批量操作及反馈

执行前显示所选范围、数量和操作；跨页选择必须明确是当前页还是全部筛选结果。首批以合理数量上限及单事务保证完整性，暂不支持需要复杂恢复机制的超大批操作。

提供当前页面会话内最近一次批量整理的撤销。撤销先校验相关数据未被后续修改，否则整体拒绝并说明冲突；页面重载后撤销入口消失，不能暗示已持久保存完整操作历史。

保留、排除、恢复auto及撤销与其反馈事件在同一事务中提交。反馈写入失败时整次操作失败并提示，避免状态和评估记录分离。反馈只记录用户实际操作，不根据旧决定推造历史事件，也不将API收藏命中记录成人工正例。

### 6.3 性能

先用100视频/500会话和2000视频/10000会话测量首次加载、筛选、详情及备份，记录相同设备的2.1.2基线；10000视频/50000会话留作需要时的压力检查。

保留现有前端分页；实际瓶颈若来自全量读取和重算，先合并刷新、按受影响bvid读取，并在页面重新可见及重启时核对最新数据。事件通知只用于减少延迟，不能成为唯一一致性依据。

需要持久化摘要或缓存时，缓存键覆盖证据版本、模型版本、参数hash及特征schemaVersion；模型切换必须使受影响缓存失效。动态评分无法仅靠sessions索引进行按分数分页；是否引入派生摘要，应依据测量决定。使用数据库游标时固定排序规则，筛选或数据版本变化后重置游标。

不提前引入虚拟列表、倒排索引或向量库。开发者在基线测量后给出本设备性能目标，随本批交付验收，不在缺少测量时编造毫秒门槛。

## 七、交付B：片段回找与简短笔记

### 7.1 最小闭环

在B站视频页主动保存当前时间点及可选名称 → 编辑简短笔记 → 在资料库检索 → 跳回相同CID及时间。首版提供纯文本Markdown编辑、保存状态、本地正文搜索及Markdown导出；不要求富文本编辑器或HTML预览。

`Marker`保存稳定ID、bvid、cid、保存时part、startSec、可选endSec、label及修订时间。`Note`保存稳定ID、bvid、可选markerId、contentMarkdown及修订时间。正文以Note为唯一真源，不再同时维护Marker.note；旧`LibraryDecision.note`原位保留并参与搜索。

第一批只做单点标记；区间、快捷键及播放器悬浮按钮在最小闭环通过后增加。笔记与标记完整加入v2备份后才能发布。

### 7.2 保存位置

复用采集器已绑定的媒体状态，由内容脚本在同一次操作返回bvid/cid/part/currentTime/duration；切P、路由或媒体源未确认时提示稍后重试。拒绝非有限数值、负时间、错误身份和超过对应CID时长的标记。

主动标记允许暂停、后台或关闭自动记录时使用，只要媒体身份能够单独确认；不得为此恢复自动追踪，也不套用有效观看计分门槛。必要元数据查询使用独立的主动操作入口及校验，不复用“自动记录已暂停即禁止查询”的路径。

### 7.3 回跳及失效

以CID查询该视频最新pages，解析当前part后生成`p`和`t`链接。网络不可用或身份无法确认时保留标记并提示，禁止静默把旧part当作已确认目标；可让用户另行打开视频首页。

CID删除或替换后标记显示来源失效，笔记仍可查看及导出。正常播放内容仍受平台可用性影响，验收目标为“来源仍存在、可访问且身份可确认时，定位到正确分P及时间”，不承诺永久可播放。

自动保存应显示未保存、保存中、已保存或失败，失败时保留编辑文本并允许重试；跨页面编辑按修订信息检测冲突。导出链接、文件名及Markdown正文做必要转义，若以后增加预览则使用安全渲染。

## 八、交付C：可复现的评分实验

### 8.1 v1与实验版本

v1完整保留现有公式、四项贡献、候选门槛及人工状态优先级；未验证更好的实验模型不得静默替换默认值。需要运行第二个模型时再抽离纯评分函数，避免仅为预留接口提前重构。

评分输出包含模型版本、参数hash、证据/特征版本、分数、类型明确的贡献明细及理由。模型只产生自动判断，最终状态由固定的人工决定优先规则合成；整理状态不参与此过程。

实验同时评估覆盖权重和持续投入目标。在180/181秒、1200/1201秒及新增观察分P时检查分数变化。明确采用单P、已观察CID合计还是整套时长，不混用分母。保留“已观察分P覆盖率”，只有完整分P清单及有效时长齐全时才计算整套覆盖率，否则显示未知。

证据充分程度单列，可描述缺失元数据、有效观看量及证据来源；不称为喜欢概率，也不与当前喜好分循环互相证明。

### 8.2 决策时证据

整理阶段的反馈事件至少包含：eventId、bvid、实际action、可选reason、操作前后人工状态、scoreAtDecision、modelVersion、完整非敏感参数或其可恢复引用、configHash、evidenceSchemaVersion、evidenceHash、createdAt。

每次有效保留/排除反馈内嵌该视频的不可变证据快照：当时相关累计会话、区间、投入、重访所需时间、互动及其观测时间、模型实际使用的元数据。只保存hash而不保存快照不能满足复现要求。快照作为反馈真源随备份保存；后续模型若需快照没有的特征，应标注该样本不可评估，不能补入未来数据冒充当时证据。

撤销事件具有targetEventId并指向被撤销的事件；原事件不删除。恢复auto表示撤回人工判断，整理性exclude和暂不处理不自动成为“不喜欢”标签。首次评分实验前应明确这些操作到评估标签的映射。

### 8.3 评估规则

先做描述性评估：高分中明确保留比例、高分明确排除比例、低分明确保留比例及小幅证据更新后的排序变化；每项报告已审核分母、样本量和样本来源。未处理视频不当负例，自动keep不当人工正例。

调参与评估按视频或时间划分，避免同一视频的相近快照同时进入两边。随机审核低分可改善覆盖，但不足以自动消除偏差；若要估计全体效果，再记录曝光、抽样层和入样概率，采用对应分层或加权方法。

数据不足时只展示探索性结果，不宣布新模型更准确。不设“积累几十条就能训练”的固定门槛；保留后回看率也须在稳定的观察窗口及采集边界下解释。个性化训练另行评估。

## 九、交付D：来源明确的智能辅助

### 9.1 顺序与前置验证

先做确定性关键词/标签建议，再导入字幕和验证一个模型提供方；之后增加标签建议、字幕摘要及章节，最后再评估查询改写和向量检索。没有AI时整理、搜索、笔记与备份完整可用。

字幕先支持用户导入SRT/VTT及明确schema的JSON，按bvid/cid关联。保留原始文本或可完整重建的内容、语言、时间段、来源、获取时间、sourceId、版本/hash和解析器版本。修订字幕生成新的源版本；已有AI结果引用的版本保留，直到用户明确删除关联内容。

B站字幕只接入经验证可访问及符合授权条件的来源；开放平台入口不作为字幕可用的证据。没有字幕时，仅做基于标题、简介或用户笔记的有限建议并标明输入范围。

浏览器内置AI的具体版本、执行上下文、下载、硬件及中文能力尚未完成本项目验证。它是可选实验路径，不作为核心功能依赖或既定可用能力。

### 9.2 最薄适配与任务生命周期

先验证单一提供方，在真实差异出现后统一少量契约：能力/语言及不可用原因、可取消调用、明确的错误结果。必要时区分不可用、待下载、下载中和可用；规则标签推荐继续使用本地函数，不为统一而强行包装成文本生成。

生成结果先按任务校验：标签为受限候选，章节时间属于目标CID范围，摘要记录实际输入范围。用户确认后才写入正式标签等对象。原始响应文本不能直接作为可信结构化结果。

首版由打开的扩展页面执行请求；关闭页面取消未完成请求，完成并校验后才事务保存。具有超时、取消、并发和重试上限；重新发起前明确前次状态，避免重复收费。暂不建立跨Service Worker重启的后台任务系统。

自定义服务按配置域名申请必要权限；开发原型验证请求权限、CORS及实际执行上下文。Cookie等平台凭据不发给模型，模型凭据只发往其明确配置的服务；普通备份不含密钥。

### 9.3 来源与隐私

每个AI结果保存artifactId、目标bvid/cid、任务类型、源ID及版本/hash、提供方、模型、promptVersion、generatedAt、经校验内容及reviewStatus。来源变化时标为过期，不自动覆盖旧结果或个人笔记。

云端模型默认关闭，启用和调用时显示将发送的范围；不自动加入完整资料库。外部字幕等只作不可信数据，不能触发工具执行或改变系统指令。支持删除结果、源文本和提供方配置，并对相互依赖的删除说明影响。

全文搜索优先利用标题、UP主、旧备注、笔记及已存字幕；是否建立倒排索引取决于测量。查询改写需保留原词检索和无模型回退。向量检索只有在实际收益明确后引入，缓存隔离模型、版本、维度及切分策略。

## 十一、验证与发布约束

验证沿用Vitest、fake-indexeddb、TypeScript及现有浏览器脚本，按本阶段实际改动增加必要场景：

- 数据阶段重点为迁移事务、备份全量校验/原子应用、重复导入、关联冲突和删除信息往返；不只比较记录数，还核对关键内容。
- 整理阶段验证一条完整用户闭环及一次批量失败/撤销冲突；不为每个简单按钮建立重复端到端测试。
- 片段阶段覆盖切换中的媒体身份、等长分P、重排/删除、对应CID时长和重启持久化。
- 评分阶段覆盖v1固定样本、180/1200秒边界、多P新增及决策时快照；旧真实样本仅作私有回归，不以两视频样本证明模型优劣。
- AI阶段才增加无模型、结构错误、超时/取消、来源更新及云端发送范围检查。

运行相称的`pnpm test`、`pnpm compile`，运行代码或构建入口改变时执行相应构建。使用现有冻结锁文件，不为方案实施升级无关依赖；只格式化实际修改文件。对外多浏览器发布前跑相应构建和发布核验，构建通过不等于对应浏览器实机能力通过。

既有真实采集待确认项继续在02_STATUS.md保留，按新功能依赖补验，不为规划任务重跑全部发布流程。数据仍放本地排除目录；源码包及公开提交继续排除用户备份、凭据和本机证据。推送、商店与Release遵循当次明确授权。
